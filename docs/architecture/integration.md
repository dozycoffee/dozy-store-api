# 외부 연동과 운영 값

> 아키텍처 개요는 [README](README.md)를 본다. 연동의 계약(무엇을 주고받는지)은 [요구사항](../requirements.md) 7장이 원본이고, 여기에는 **어떻게 구현하고 어떤 값으로 운영하는지**를 둔다.

## Catalog 호출과 캐시

Store는 Catalog의 표시용 상품 정보를 조회한다([ADR-0002](../adr/0002-minimal-product-replica-with-full-state-events.md)). 판단용 상태는 이벤트로 복제하므로 여기서 다루지 않는다.

| 호출 | 쓰는 곳 | 캐시 |
|---|---|---|
| 상품 기준 정보 ID 목록 조회 | 매니저 화면(매장 상품 목록), 손님 메뉴 | 매니저 화면은 캐시하지 않는다. 손님 메뉴는 상품별로 짧게 캐시한다 |
| 카테고리 목록 | 매니저 화면, 손님 메뉴 | 캐시한다 |
| 유효 옵션 구성 (상품 하나) | 매니저 화면 상품 상세, 손님 메뉴 상품 상세 | 손님 메뉴만 상품별로 짧게 캐시한다 |
| 전체 상품 상태 목록 | 복제본 채우기·다시 맞추기 | 캐시하지 않는다 |

- 호출은 스타터의 `dozySystemWebClient`로 하고, 응답은 `catalogproduct.adapter.outbound.catalog`에서 Store의 타입으로 번역한다. 다른 모듈은 이 어댑터를 직접 쓰지 않고 `catalogproduct`의 조회 UseCase(`GetProductDisplayInfoUseCase` 등)로 받는다(ADR-0005).
- **매니저 화면은 캐시하지 않는다.** 매니저가 Catalog에서 바뀐 값을 바로 보는 게 낫고, 요청이 많지 않다.
- **손님 메뉴는 캐시한다.** 상품 기준 정보는 상품 ID별로 담고, 메뉴를 만들 때 캐시에 없는 상품만 모아 한 번에 조회한다.
- 캐시는 인스턴스별 인메모리(Caffeine)다. 인스턴스마다 값이 캐시 시간만큼 다를 수 있다. 손님 메뉴는 앞단 HTTP 캐시가 있어 이 차이가 크게 드러나지 않는다.
- 캐시를 Catalog 이벤트로 비우지 않는다. 표시용 정보는 이벤트로 오지 않기 때문이다(ADR-0002). 시간이 지나면 만료된다.
- 시간 초과·연결 실패·5xx는 `CatalogUnavailableException`으로 바꾸고, 그 조회 전체를 `503`으로 돌려준다. 일부만 보여 주지 않는다(요구사항 5.1). 조회(GET)는 한 번 재시도한다.
- 서킷 브레이커는 지금 두지 않는다. Catalog 장애 때 호출이 쌓여 응답이 느려지는 게 보이면 도입한다.

## 메시지 소비

메시징 기술과 이벤트 공통 규약이 정해지면 확정한다. 지금은 Kafka를 전제로 한 원칙만 둔다.

| 구독 | 보낸 곳 | 키 | 반영 |
|---|---|---|---|
| 상품 이벤트 | Catalog | 상품 ID | `catalogproduct`의 스냅샷 적용 유스케이스 |
| 재고 이벤트 (2단계) | 정해지지 않음 (요구사항 8장) | (규약에 따름. 매장 코드 + SKU 권장) | `storeproduct`의 재고 반영 유스케이스 |

- **컨슈머 그룹은 Store 서비스 하나**다. 인스턴스가 여럿이어도 파티션을 나눠 받는다.
- **중복과 순서**: 상품 이벤트는 순번, (2단계) 재고 이벤트는 발생 시각으로 걸러 낸다. 그래서 "최소 한 번" 전달이면 충분하다.
- **오프셋은 처리 트랜잭션이 커밋된 뒤에 커밋한다.** 처리 중 죽으면 같은 메시지를 다시 받고, 위 거르기로 중복이 무해하다.
- **처리할 수 없는 메시지**는 [예외 구조](exception.md#http가-아닌-경로-메시지-소비)대로 격리한다(DLQ 예정).
- **복제본 채우기**: Store를 처음 띄울 때는 상품 이벤트 구독을 시작한 뒤 Catalog의 전체 상품 상태 목록으로 복제본을 채운다. 둘 다 순번으로 거르므로 순서가 섞여도 최신 상태가 남는다. 절차는 운영 문서로 따로 쓴다.

## 인증

[기술 스택의 인증 설정](tech-stack.md#인증-설정)을 따른다.

- Store는 realm `internal`(본사 직원, Catalog 서비스 계정)과 `partner`(점주)를 받는다.
- **역할과 계정 종류는 컨트롤러 메서드의 `@PreAuthorize`로 검사한다.** 스타터의 기본 필터 체인(토큰 검증, `public-paths` 밖의 모든 요청은 인증 필요)을 그대로 쓰고 경로별 인가 규칙은 따로 두지 않는다. 엔드포인트마다 인가 조건이 컨트롤러에 보이고, 필터 체인을 직접 교체하지 않아도 되기 때문이다. WebFlux에서는 `suspend` 함수에 붙인다.
   * 여러 realm을 받는 서비스는 모든 API에 계정 종류(type) 조건을 붙인다(스타터의 안내).
   * 역할은 접두사를 뗀 코드로 판단한다. 스타터가 `store:` 역할만 남기고 접두사를 떼므로 `store:admin`은 `hasRole('admin')`이다. 코드는 `StoreRoles` 상수를 쓴다.
   * 계정 종류 조건은 `authentication.principal.key.type.name() == 'EMPLOYEE'`처럼 쓴다. `@dozyAuth.isType(...)`는 단독으로는 동작하지만, WebFlux에서는 `Mono<Boolean>`이라 `and`로 다른 조건과 묶으면 평가에 실패해 500이 난다.
   * 역할 코드(`StoreRoles`)와 이 표현(`StoreAuthorization`)은 모든 모듈의 컨트롤러가 함께 쓰므로 `common.security`에 한 곳으로 둔다. 모듈의 adapter는 서로 참조할 수 없어서 모듈 안에 두면 모듈마다 복사하게 된다.
- **매니저 검사(principal key와 매니저 지정 비교)는 `management`의 `CheckStoreAccessUseCase`가** 한다. 다른 모듈의 유스케이스는 이 UseCase를 같은 트랜잭션 안에서 부른다(ADR-0005). 매니저 지정은 DB를 봐야 해서 `@PreAuthorize`만으로는 판단할 수 없다.
- Store의 서비스 계정 id·secret은 Auth 관리자가 발급하고, 배포 설정의 비밀값으로 넣는다. secret은 저장소에 두지 않는다. 교체하면 배포 설정을 바꾸고 서비스를 다시 띄운다.

## 공개 경로

- `/api/v1/public/**`는 스타터의 `public-paths`로 토큰 없이 허용한다.
- 요청 제한은 IP 단위 인메모리 버킷(Bucket4j)으로 `common.web`의 필터에서 한다. 키오스크나 매장 와이파이처럼 여러 손님이 IP 하나를 쓰는 경우가 있으므로 한도를 넉넉하게 둔다. 프록시 뒤에서는 신뢰하는 프록시의 `X-Forwarded-For`로 IP를 정한다.
- 응답에 `Cache-Control: public, max-age=…`를 붙인다. 오류 응답(404 등)은 캐시하지 않는다(`no-store`).

## 운영 값

출시 전에 정하고 운영하며 조정한다. 아래는 **임시 초기값**이며 근거가 생기면 바꾼다. 설정 키 이름은 구현 때 정한다.

| 값 | 임시 초기값 | 정할 때 볼 것 | 관련 |
|---|---|---|---|
| 반영 지연 목표치 | 보통 수 초, 1분 넘으면 알림 | 상품 이벤트 컨슈머 지연(lag) | 요구사항 3.1 |
| 손님 메뉴 HTTP 캐시 (`max-age`) | 30초 | 품절·숨김이 늦게 보여도 되는 시간 | 요구사항 5.2, 손님 API |
| 손님 메뉴용 표시 정보 캐시 | 5분 | 가격·이름 변경이 늦게 보여도 되는 시간 | 요구사항 5.2 |
| 카테고리 목록 캐시 | 10분 | 카테고리 변경 빈도 | 요구사항 5.1 |
| 공개 경로 요청 제한 | IP당 1분에 120회 | 매장 와이파이·키오스크처럼 IP를 공유하는 경우 | 요구사항 5.2 |
| Catalog 호출 시간 초과 | 연결 1초, 응답 2초, 조회 재시도 1회 | 매니저 화면 응답 시간 목표 | 요구사항 5.1 |
| (2단계) 보관 재고 이벤트 기한 | 7일 | 정상 지연(수 초)보다 충분히 긴 시간. 재고 연동 방식이 정해진 뒤 확정 | 요구사항 8장 |
| 메시지 처리 재시도 | 3회 후 격리 | 이벤트 공통 규약 | [예외 구조](exception.md) |
| 규모 가정 | 매장 수천, 상품 수백~수천, 매장당 메뉴 수백 | 위 값들과 인덱스·캐시 크기의 근거 | 전체 |

이 값들이 정해지면 요구사항의 "운영하며 정함" 표현은 그대로 두고, 확정 값은 이 표와 설정 파일에만 둔다. 운영 값은 규칙이 아니기 때문이다.
