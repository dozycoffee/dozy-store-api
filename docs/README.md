# 문서 안내

Store 서비스의 명세 원본이다. 수정은 코드와 마찬가지로 PR로 하고, 설계를 바꾸는 코드 PR에서는 관련 문서도 함께 고친다.

각 문서는 한 가지 질문에만 답한다. 같은 내용을 두 문서에 적지 않고, 다른 문서의 내용이 필요하면 절 번호나 링크로 참조한다.

| 문서 | 답하는 질문 | 담는 것 | 담지 않는 것 |
|---|---|---|---|
| [요구사항](requirements.md) | 무엇을 해야 하는가 | 기능별 액터 행위와 비즈니스 규칙, 노출 판단 로직, 다른 서비스와 주고받는 계약. 모든 규칙의 원본 | 구현 방법, 클래스·테이블 이름, 단계별 흐름 |
| [시나리오](scenarios.md) | 여러 참여자와 시점에 걸쳐 어떤 순서로 일어나는가 | 여러 애그리거트·외부 서비스·시점이 얽히는 흐름의 참여자, 단계, 예외 흐름 (통합 테스트 기준) | 규칙 원문(요구사항 절 번호로 참조), 단순 CRUD |
| [도메인 모델](domain-model.md) | 규칙을 어떤 모델로 지키는가 | 경계, 애그리거트 책임과 참조 관계, 변경 메커니즘, 불변식과 강제 위치, 상태 전이, 도메인 이벤트, 용어집 | 필드 목록(ERD·코드), 규칙 원문 |
| [ERD](erd.md) | 어떻게 저장하는가 | 테이블·컬럼·제약, 상태값, 동시성 처리, 감사 컬럼 정책 | 비즈니스 규칙 |
| [아키텍처](architecture/README.md) | 어떤 기술로, 코드를 어떻게 구성하는가 | 기술 스택, 패키지 구조, 예외 구조, 테스트, 영속성, 외부 연동과 운영 값, 미정 사항 | 도메인 규칙 |
| [API 명세](api/README.md) | 외부에 어떤 계약으로 제공하는가 | 엔드포인트, 요청·응답 형식, 오류 코드, 인가, 공통 규약 | 규칙 원문(요구사항 절 번호로 참조), 구현 방법 |
| [ADR](adr/README.md) | 왜 그렇게 정했는가 | 되돌리기 비싼 결정의 맥락, 검토한 대안, 결과. 채택 후에는 고치지 않고 새 ADR로 대체 | 현재 규칙(각 문서에 둠) |

**수정 순서**: 규칙이 바뀌면 요구사항 → (영향받는) 시나리오 → 도메인 모델 → ERD 순서로 반영한다. 구현 중 규칙과 다른 결정을 내렸다면 요구사항부터 고친다. 되돌리기 비싼 결정이면 같은 PR에 ADR을 추가한다.

## 표기

- **(2단계)**: 재고 연동 때 붙일 규칙·모델·테이블이다. 1단계(첫 출시)에는 만들지 않는다. 요구사항 8장에 모았다.
- **다른 서비스**: Store가 연동하는 서비스는 다음 이름으로 부른다. Store 문서는 그 서비스의 내부를 다루지 않고, Store가 기대하는 계약만 적는다(요구사항 7장).

| 이름 | 하는 일 (Store가 보는 범위) |
|---|---|
| Catalog | 상품 정의와 판매 범위의 원본. 상품 이벤트를 보내고 상품 정보를 조회하게 해 준다 |
| Auth | 계정과 토큰을 발급한다. Store는 토큰을 검증한다 |
| 재고 서비스 | 창고 재고의 원본. 1단계에서는 연동하지 않는다 |
