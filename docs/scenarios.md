# Store 시나리오

> 문서별 역할과 수정 순서는 [문서 안내](README.md)를 참고한다. 규칙 자체는 [요구사항](requirements.md)이 원본이며, 각 단계의 `(요구사항 N.N)`은 근거가 되는 절을 가리킨다.

여러 참여자·외부 서비스·시점이 얽히는 흐름만 다룬다. 단순 CRUD(매장 정보 수정 등)는 다루지 않는다.

**참여자**

| 참여자 | 설명 |
|---|---|
| 본사관리자 | 매장 관리 권한으로 매장 등록·상태 전환·매니저 지정을 한다. 매장 설정도 바꿀 수 있다 |
| 매장 매니저 | 매니저로 지정된 매장의 진열·노출·수동 품절을 관리한다 (점주, 직영점 점장) |
| 손님 | 로그인 없이 매장과 메뉴를 본다. 앱·웹·키오스크 등 어느 채널이든 같은 메뉴다 |
| 본사 화면 (또는 BFF) | 본사관리자의 화면. Catalog와 Store의 결과를 합친다 |
| Auth | 계정과 토큰의 원본. 본사 화면이 매니저로 지정할 계정을 찾을 때 쓴다 (외부) |
| Catalog | 상품 정의·상태·판매 범위의 원본. 상품 이벤트를 발행하고 상품 기준 정보를 제공한다 (외부) |
| 재고 서비스 | 1단계에서는 연동하지 않는다. S6은 2단계(재고 연동) 검토용이다 (외부) |

## S1. 매장 등록부터 개점까지

**참여자**: 본사관리자, 본사 화면(또는 BFF), Auth, Catalog, 매장 매니저, 손님

**기본 흐름**
1. 본사관리자가 매장명, 주소, 매장 전화번호, 개점 예정일을 입력해 매장을 등록한다. (요구사항 1.1)
2. 매장이 `Preparing` 상태로 생성되고 매장 코드가 부여된다. (요구사항 1.1, 1.2)
3. 본사관리자가 이 매장의 매니저를 지정한다. S3의 흐름을 따른다. (요구사항 1.3)
4. 본사관리자가 Catalog에서 상품의 판매 범위에 이 매장을 넣는다. 대상 매장은 Store의 매장 목록에서 고르고(본사 조회 권한), Catalog는 Store에 이 매장을 지정할 수 있는지 확인한다. (요구사항 1.4, 7.2)
5. 매니저는 개점 전에 진열 순서와 노출 여부를 준비한다. (요구사항 1.4, 3장)
6. 이 동안 손님에게는 매장의 요약 정보만 "오픈 예정"으로 보이고, 메뉴는 보이지 않는다. (요구사항 1.4, 4장 0단계)
7. 본사관리자가 개점을 요청한다. 매장이 `Open`이 되고 개점일이 실제 개점한 날로 바뀐다. (요구사항 1.2)
8. 손님에게 매장의 상세 정보와 메뉴가 보인다. 메뉴는 매니저가 준비해 둔 진열·노출 설정을 따른다. (요구사항 1.4, 4장)

**대체 흐름**
- 1a. 개점이 미뤄지면 → 본사관리자가 `Preparing`인 동안 개점 예정일을 바꾼다. 손님에게 보이는 개점 예정일도 바뀐다. (요구사항 1.2, 1.4)
- 3a. 매니저를 아직 정하지 못했으면 → 매니저 없이 진행할 수 있다. 그동안 매장 설정은 본사관리자만 바꿀 수 있다. (요구사항 1.3)
- 7a. 개점 전에 매장을 열지 않기로 하면 → 폐점한다. 매장은 삭제할 수 없다. S2의 폐점 흐름을 따른다. (요구사항 1.1, 1.2)

**예외 흐름**
- 1b. 폐점하지 않은 다른 매장과 같은 이름이면 → 등록 거부 (요구사항 1.1)
- 7b. 이미 `Open`인 매장을 개점하려 하면 → 거부 (요구사항 1.2)

## S2. 휴업과 폐점

**참여자**: 본사관리자, 매장 매니저, 손님, Catalog

**기본 흐름 (휴업과 재개)**
1. 본사관리자가 `Open`인 매장의 휴업을 요청한다. 매장이 `Suspended`가 된다. (요구사항 1.2)
2. 손님에게는 매장의 요약 정보만 "휴업 중"으로 보이고, 상세 정보와 메뉴는 보이지 않는다. 상세를 요청해도 거부하지 않고 요약만 보여 준다. (요구사항 1.4, 4장 0단계)
3. 매니저는 휴업 중에도 진열·노출·수동 품절을 바꿀 수 있다. (요구사항 1.4)
4. 본사관리자가 재개를 요청한다. 매장이 `Open`이 되고, 휴업 중에 바꾼 설정과 품절 상태가 그대로 쓰인다. (요구사항 1.2)

**기본 흐름 (폐점)**
1. 본사관리자가 폐점을 요청한다. `Preparing`·`Open`·`Suspended` 어느 상태에서든 할 수 있다. 매장이 `Closed`가 되고 폐점일이 기록된다. (요구사항 1.2)
2. 손님에게 매장이 보이지 않는다. (요구사항 1.4)
3. 매니저 지정은 유지된다. 매니저는 폐점한 매장을 읽기 전용으로 본다. (요구사항 1.3, 1.4)
4. Catalog의 판매 범위에는 이 매장이 그대로 남는다. Store는 Catalog에 폐점을 알리지 않는다. (요구사항 1.2)
   - 이 매장은 노출 판단 0단계에서 걸리므로 어떤 상품도 노출되지 않는다. (요구사항 4장)
   - 노출 현황의 판매 가능 매장 수와 매장별 상세에서 빠진다. 본사 화면은 판매 범위에 남은 이 매장을 폐점으로 표시한다. (요구사항 1.2, 6장)
5. 이 매장의 이름은 새 매장에 다시 쓸 수 있다. (요구사항 1.1)

**예외 흐름**
- 휴업 1a. `Open`이 아닌 매장을 휴업하려 하면 → 거부 (요구사항 1.2)
- 폐점 이후. 폐점한 매장을 재개·개점하려 하면 → 거부. 다시 영업하려면 새 매장으로 등록한다. (요구사항 1.2)
- 폐점 이후. 매니저가 폐점한 매장의 설정을 바꾸려 하면 → 거부 (요구사항 1.4, 3.1)
- 폐점 이후. 폐점한 매장에 매니저를 새로 지정하려 하면 → 거부 (요구사항 1.3)
- 폐점 이후. 본사관리자가 Catalog에서 폐점한 매장을 판매 범위에 새로 넣으려 하면 → Catalog가 Store 확인 결과에 따라 거부 (요구사항 7.2)
- 폐점 이후. 폐점 전에 등록된 판매 범위 예약이 이 매장을 포함하고 있으면 → 예약은 그대로 적용된다. 노출은 0단계가 막는다. (요구사항 7.2)

## S3. 매니저 지정과 해제

**참여자**: 본사관리자, 본사 화면(또는 BFF), Auth, 매장 매니저

**기본 흐름**
1. 본사관리자가 본사 화면에서 매니저로 지정할 계정을 찾는다. 본사 화면이 Auth에서 활성 계정의 이름과 마스킹된 연락처를 받아 본인인지 확인한다. Store는 이 단계에 관여하지 않는다. (요구사항 1.3)
   - 점주(파트너 계정)는 이메일로 찾는다.
   - 본사 직원도 찾을 수 있어야 한다. 이 직원은 Auth에서 매장 매니저 역할을 미리 받아 두어야 한다.
2. 본사관리자가 이름과 연락처로 본인인지 확인하고 지정을 요청한다. Store는 요청의 principal key(계정 종류와 계정 ID)를 그대로 저장한다. (요구사항 1.3)
3. 매니저가 로그인하면 자기가 매니저인 매장 목록을 보고, 매장을 골라 관리한다. (요구사항 1.4, 5.1)
4. 매니저의 요청이 오면 Store는 토큰을 검증하고, 요청한 매장의 매니저인지 확인한다. (요구사항 2장)

**대체 흐름**
- 2a. 한 계정을 여러 매장에, 한 매장에 여러 계정을 지정할 수 있다. 같은 매장의 매니저는 모두 같은 권한이다. (요구사항 1.3)
- 2b. 매니저를 교체하면 → 기존 매니저의 지정을 해제하고 새 매니저를 지정한다. 매장의 진열·노출·수동 품절 설정은 그대로다. (요구사항 1.3)
- 4a. 매니저가 Auth에서 탈퇴·퇴사하거나 정지되면 → 토큰을 받을 수 없어 요청할 수 없다. 남은 지정은 본사관리자가 해제한다. (요구사항 1.3)

**예외 흐름**
- 1a. Auth에 없거나 활성이 아닌 계정이면 → 본사 화면에서 찾을 수 없어 지정하지 못한다. (요구사항 1.3)
- 2c. 이미 그 매장의 매니저인 계정을 다시 지정하면 → 거부 (요구사항 1.3)
- 2d. 계정 ID 형식이 잘못됐거나 계정 종류가 `partner`·`employee`가 아니면 → Store가 거부. 형식이 맞지만 없는 계정이면 Store는 알 수 없어 저장된다. 그 계정으로는 토큰을 받을 수 없으므로 아무도 매장을 관리하지 못하고, 본사관리자가 해제한다. (요구사항 1.3)
- 2e. 폐점한 매장에 매니저를 새로 지정하려 하면 → 거부. 폐점 전에 지정된 매니저는 그대로 남는다. (요구사항 1.3)
- 4b. 매니저로 지정되지 않은 매장의 설정을 바꾸거나 조회하려 하면 → 거부. 계정 ID가 같아도 계정 종류가 지정과 다르면 매니저가 아니다. (요구사항 1.3, 2장)
- 4c. 매장 매니저 역할이 없는 본사 직원은 Store를 호출할 수 없다. 매니저로 지정돼 있어도 요청이 거부된다. (요구사항 1.3)

## S4. 매장 상품 관리

**참여자**: 매장 매니저, Catalog

**기본 흐름**
1. 매니저가 매장의 상품 목록을 조회한다. (요구사항 5.1)
   - Store가 상품 복제본에서 `Active`이고 이 매장이 판매 범위에 든 상품을 고르고, 이 매장의 진열 설정과 판매 가능 여부를 함께 읽는다.
   - 그 상품 ID 목록으로 Catalog에서 상품 기준 정보(표시용 시작가 포함)를 한 번에 받고, 캐시해 둔 카테고리 목록으로 카테고리 이름을 붙인다.
   - 진열 순서를 정한 상품이 앞에, 정하지 않은 상품이 뒤에 상품 ID 순으로 놓인다. 숨긴 상품도 포함한다. (요구사항 3.3)
   - 개별 설정이 없는 상품은 기본값(노출)으로, 품절 여부는 매니저의 수동 품절(없으면 판매중)을 따른다. 1단계에서는 재고 추적 상품도 같다. (요구사항 3.4, 4장)
2. 매니저가 어떤 상품을 숨기거나, 진열 순서를 완성해 최종 순서 전체를 한 번에 저장한다. 수동 품절도 할 수 있다(1단계에서는 재고 추적 상품도). (요구사항 3.2, 3.3, 3.4)
   - 진열 순서는 저장한 목록의 순서대로 정해지고, 목록에 없는 상품은 순서를 정하지 않은 상품이 된다. 순서는 한 번에 모두 반영된다.
3. 그 상품에 대한 이 매장의 개별 설정이 아직 없으면 이 시점에 기본값으로 만든 뒤 변경을 반영한다. 동시에 요청이 들어와도 개별 설정은 매장·상품당 하나만 생긴다. (요구사항 3.1)
4. 이후 노출 판단은 저장된 값을 따른다. 품절이어도 숨기지 않았다면 노출되며 구매 불가로 표시된다. (요구사항 3.4, 4장)
5. 매니저가 상품 하나를 열면 Store가 Catalog에서 그 상품의 유효 옵션 구성을 받아 그대로 보여 준다. (요구사항 5.1)

**대체 흐름**
- 2a. 판매 범위에 든 `Discontinued` 상품의 설정도 바꿀 수 있다. 바꿔 둔 설정은 재활성화된 뒤 그대로 쓰인다. (요구사항 3.1)

**예외 흐름**
- 1a. Catalog가 응답하지 않으면 → 목록 조회 전체가 실패한다. 일부만 보여 주지 않는다. (요구사항 5.1)
- 2c. 자기 매장이 판매 범위에 포함되지 않은 상품의 설정이나 품절을 바꾸려 하면 → 거부. 진열 순서 목록에 그런 상품이 하나라도 있으면 전체를 거부한다. (요구사항 3.1)
- 2d. 폐점한 매장의 설정을 바꾸려 하면 → 거부 (요구사항 3.1)
- 2e. 가격을 바꾸려 하면 → 해당 기능 없음 (요구사항 2장)

## S5. Catalog 상품 변경의 반영

**참여자**: Catalog, 매장 매니저

**기본 흐름**
1. Catalog에서 상품이 등록·활성화·단종·삭제되거나 판매 범위가 바뀐다. Catalog는 변경과 같은 트랜잭션에 이벤트를 기록하고 발행한다. 이벤트에는 상품 상태 전체(상품 ID, SKU, 상태, 판매 범위, 재고 추적 여부)와 상품별 순번이 담긴다. (요구사항 7.1)
2. Store가 이벤트를 받아 복제본의 순번과 비교한다. 복제본보다 새로운 이벤트면 담긴 상태로 복제본을 교체한다. (요구사항 3.5)
3. 판매 범위가 바뀌었으면, 이 상품의 매장 설정 중 새 판매 범위에 들지 않는 매장의 개별 설정과 수동 품절을 삭제한다. (요구사항 3.5)
4. 단종됐으면 매장의 개별 설정은 그대로 두고, 노출 판단 1단계에서 모든 매장이 비노출된다. 재활성화되면 보존된 설정이 그대로 쓰인다. 단종 전에 숨겨 둔 매장은 계속 숨김이다. (요구사항 3.5, 4장)
5. 삭제됐으면 그 상품의 매장 데이터를 모두 삭제하고, 복제본에는 삭제 사실을 남긴다. (요구사항 3.5)
6. 매니저와 손님은 다음 조회부터 바뀐 상태를 본다.

**대체 흐름**
- 2a. 이미 반영한 것보다 오래된 이벤트나 중복 이벤트가 오면 → 무시한다. 이벤트가 상태 전체를 담으므로, 종류가 다른 이벤트끼리 순서가 뒤바뀌어 오래된 쪽을 버려도 정보를 잃지 않는다. (요구사항 3.5, 7.1)
  - 예: 순번 6 "활성화됨"을 먼저 반영한 뒤 순번 5 "판매 범위 바뀜"이 도착하면 버린다. 순번 6의 상태에 바뀐 판매 범위가 이미 담겨 있다.
- 2b. 삭제된 상품의 오래된 이벤트가 늦게 도착하면 → 삭제 사실이 남아 있으므로 무시한다. 상품이 다시 살아나지 않는다. (요구사항 3.5)
- 2c. 처음 등록된 상품이면 → 복제가 시작된다. (재고 연동 후에는 이 상품의 SKU로 보관해 둔 재고 이벤트를 반영한다, S6 3d, 요구사항 8장)
- 2d. 복제본을 처음 채우거나 다시 맞출 때는 → Catalog의 전체 상품 상태 목록을 받아, 이벤트와 같은 방식(순번 비교, 상태 교체, 판매 범위 정리)으로 반영한다. (요구사항 7.1)

**예외 흐름**
- 반영이 늦어지는 동안에는 Store가 옛 상태로 판단한다. 예: 단종된 상품이 잠깐 손님에게 보인다. 목표 시간을 넘기면 운영자가 알 수 있게 한다. 주문 시점의 검증은 주문·POS의 책임이다. (요구사항 3.1)

## S6. 재고 추적 상품의 품절과 해제 — 2단계, 보류

**참여자**: 재고 서비스(또는 매장 재고를 알려 줄 서비스), Catalog, 매장 매니저

> **1단계에서는 이 흐름이 없다.** 재고 추적 상품도 매니저가 품절을 직접 관리한다(S4, 요구사항 3.4). 아래는 매장 재고를 어느 서비스가 이벤트로 알려 준다는 전제의 1차 검토이며(요구사항 8.2), 재고 서비스는 매장 재고를 관리하지 않으므로 재고 담당과 정한 뒤 다시 쓴다(요구사항 8.1).

**기본 흐름**
1. 재고 추적 상품이 활성화되면, 판매 범위에 포함된 영업 중인 매장의 메뉴에 곧바로 나타난다. 매장 재고는 처음에 0이므로 품절로 표시된다. (요구사항 8.2, 4장)
2. 매장에 상품이 입고된다. 입고 절차 자체는 재고 서비스의 책임이다. (요구사항 8.2)
3. 재고 서비스가 "매장 재고 생김" 이벤트를 매장 코드, SKU, 발생 시각과 함께 발행한다. (요구사항 8.2)
4. Store가 매장 코드를 매장 ID로, SKU를 상품 복제본으로 상품 ID로 바꾼 뒤, 그 매장·상품의 재고 상태를 판매중으로 바꾼다. 매니저와 손님에게 품절이 해제되어 보인다. (요구사항 8.2)
5. 매장 재고가 소진되면 "매장 재고 없음" 이벤트로 품절로 바뀐다. 재입고되면 다시 판매중이 된다. (요구사항 8.2)

**대체 흐름**
- 1a. 매니저는 입고 전이라도 이 상품을 숨기거나 진열 순서를 바꿀 수 있다. 이때 만들어지는 개별 설정은 노출·진열 순서만 담고, 품절 여부에는 영향을 주지 않는다. (요구사항 3.2, 8.2)
- 3a. 상품이 단종 중이거나, 매장이 판매 범위 밖이거나, 매장이 개점 준비·휴업 중이어도 재고 이벤트는 똑같이 반영된다. 재판매·재포함·재개 시점에 현재 재고가 이미 반영되어 있다. (요구사항 8.2, S2, S5)
- 3b. 이미 반영한 것보다 오래된 이벤트나 중복 이벤트가 오면 → 무시한다. (요구사항 8.2)
- 3c. 재고 추적 상품이 아닌 상품의 이벤트가 오면 → 기록만 하고 무시한다. (요구사항 8.2)
- 3d. 복제본에 아직 없는 SKU의 이벤트가 오면 → 버리지 않고 보관한다. 상품 등록 이벤트보다 먼저 도착했을 수 있기 때문이다. 그 상품이 복제되면(S5 2c) 재고 추적 상품일 때 반영한다. 같은 매장·상품의 보관 이벤트는 가장 늦게 발생한 것만 의미가 있다. (요구사항 8.2)
- 3e. 없는 매장 코드의 이벤트가 오면 → 기록만 하고 무시한다. (요구사항 8.2)

**예외 흐름**
- 매니저가 재고 추적 상품의 품절을 직접 바꾸려 하면 → 거부 (요구사항 8.2)

> **향후**: 이벤트 유실 등으로 재고 상태가 어긋나는 경우에 대비해, 재고 서비스의 재고 조회 API가 확정되면 재활성화·판매 범위 재포함·매장 재개 시점에 재고를 다시 맞추는 흐름을 추가한다. 끝내 복제되지 않는 SKU의 보관 이벤트를 언제 버릴지도 정해야 한다(요구사항 결정이 필요한 것).

## S7. 노출 현황 조회

**참여자**: 본사관리자, 본사 화면(또는 BFF), Catalog

**기본 흐름**
1. 본사관리자가 노출 현황 화면에서 카테고리·태그·상품 그룹 조건을 고른다. 본사관리자는 Catalog의 상품 관리 역할과 Store의 본사 조회 역할(또는 매장 관리 역할)을 함께 가져야 한다. 이 직원의 토큰 하나로 두 서비스를 모두 부른다. (요구사항 2장)
2. 본사 화면이 Catalog의 상품 목록에서 조건에 맞는 상품 한 페이지를 받는다. (요구사항 6장)
3. 본사 화면이 그 상품 ID 목록으로 Store에서 상품별 판매 가능 매장 수와 노출 중인 매장 수를 한 번에 받는다. (요구사항 6장)
   - 판매 가능 매장 수: 판매 범위에 포함되고 `Open`인 매장의 수. 상품 상태와는 관계없다.
   - 노출 중인 매장 수: 그중 노출 판단을 통과한 매장의 수. 품절이어도 숨기지 않았으면 센다.
4. 본사 화면이 두 결과를 상품 ID로 합쳐 보여 준다. Catalog와 Store는 서로를 부르지 않는다. (요구사항 6장)
5. 본사관리자가 상품 하나를 열면, 본사 화면이 Store에서 그 상품의 매장별 상세 노출 정보를 받는다. 판매 범위에 든 폐점하지 않은 매장마다 매장명, 매장 상태, 노출 여부, 품절 여부, 비노출 이유가 담긴다. (요구사항 6장)
   - 비노출 이유: 매장이 `Open`이 아님, 상품이 `Active`가 아님, 매니저가 숨김
   - 개점 준비·휴업 매장도 여기서 볼 수 있다.

**대체 흐름**
- 3a. `Draft` 상품이면 → 판매 가능 매장 수는 그대로이고 노출 중인 매장 수만 0이다. (요구사항 6장)

**예외 흐름**
- 1a. Store 역할이 없는 본사관리자는 Store 조회가 거부되어 매장 수를 볼 수 없다. (요구사항 2장)
- 매장 수로 정렬하거나 거르는 조회는 지원하지 않는다. 두 서비스에 걸친 정렬이 되기 때문이다. (요구사항 6장)

## S8. 손님의 매장 찾기와 메뉴 조회

**참여자**: 손님(앱·웹, 키오스크, POS 등 어느 채널이든), Catalog

**기본 흐름**
1. 손님이 로그인 없이 매장을 찾는다. 지역이나 매장명으로 거르고, 폐점하지 않은 매장이 나온다. 개점 준비 매장은 "오픈 예정", 휴업 매장은 "휴업 중"으로 보인다. (요구사항 1.4, 5.2)
2. 손님이 매장을 고른다. `Open`인 매장이면 상세 정보(전화번호 등)까지 보인다. (요구사항 1.4)
3. 손님이 메뉴를 연다. Store가 메뉴를 만든다. (요구사항 5.2)
   - 이 매장에서 노출 판단(4장)을 통과한 상품을 고른다. 매장 상태, 상품 상태, 판매 범위, 숨김, 품절은 Store의 현재 값으로 판단하고 캐시하지 않는다.
   - 그 상품들의 표시용 정보(이름, 이미지, 가격, 카테고리, 태그, 표시용 시작가)와 카테고리 구조·노출 순서를 붙인다. 캐시에 있으면 캐시를 쓰고, 없으면 Catalog에서 받아 짧게 캐시한다.
   - 상품은 진열 순서대로, 카테고리는 본사가 정한 노출 순서대로 놓는다. 품절 상품은 구매 불가로 표시한다.
4. 채널의 화면이 받은 메뉴 안에서 카테고리 탭, 태그 모아 보기, 판매중만 보기, 이름 검색을 한다. Store에 다시 요청하지 않는다. (요구사항 5.2)
5. 손님이 상품 하나를 고르면 그 상품의 유효 옵션 구성을 받는다. Store가 이 매장 메뉴에 있는 상품인지 먼저 확인하고, 옵션 구성은 캐시나 Catalog에서 받는다. (요구사항 5.2)
6. 주문은 손님이 고른 채널이 주문·POS로 넘긴다. 주문·POS가 주문 시점의 가격을 다시 검증한다. Store는 관여하지 않는다. (요구사항 5.2)

**대체 흐름**
- 2a. 개점 준비·휴업 매장을 고르면 → 요약 정보만 보인다(개점 준비면 개점 예정일 포함). 즐겨찾기나 공유 링크로 들어와도 거부하지 않는다. (요구사항 1.4)
- 3a. `Open`이 아닌 매장의 메뉴를 열면 → 메뉴 없음으로 보인다. 오류가 아니다. (요구사항 5.2)
- 3b. 영업 중이지만 노출할 상품이 하나도 없으면 → 빈 메뉴로 보인다. (요구사항 5.2)
- 3c. 같은 매장의 메뉴를 여러 손님·채널이 연달아 열면 → 공개 응답이라 HTTP 캐시·CDN에서 바로 받을 수 있다. 품절 표시가 캐시 시간만큼 늦게 바뀔 수 있다. (요구사항 5.2)
- 3d. 매니저가 상품을 숨기거나 품절 처리하면 → 다음 메뉴부터 반영된다(HTTP 캐시 시간 이내). Catalog에서 가격·이름이 바뀌면 → Store의 표시용 정보 캐시가 만료된 뒤 반영된다. 결제 금액은 주문·POS가 검증하므로 틀리지 않는다. (요구사항 5.2)
- 3e. Catalog에서 상품이 단종되거나 판매 범위에서 빠지면 → 캐시와 관계없이 Store가 이벤트를 반영하는 즉시 메뉴에서 빠진다(S5). (요구사항 5.2, 3.1)

**예외 흐름**
- 1a. 같은 곳에서 요청이 너무 많으면 → 요청 제한으로 잠시 거부된다. (요구사항 5.2)
- 2b. 없거나 폐점한 매장이면 → 매장을 찾을 수 없다. (요구사항 1.4)
- 3f. 캐시에 없는 표시용 정보를 Catalog에서 받지 못하면 → 메뉴 조회 전체가 실패한다. 일부 상품만 빠진 메뉴를 보여 주지 않는다. (요구사항 5.1, 5.2)
- 5a. 숨겨졌거나 `Active`가 아니거나 판매 범위 밖인 상품, 또는 `Open`이 아닌 매장의 상품을 열면 → 상품을 찾을 수 없다. (요구사항 5.2)
