# ADR-0006: 매장별 진열 순서를 두지 않고 메뉴의 상품은 본사 등록 순으로 한다

- **상태**: 채택
- **날짜**: 2026-10-15
- **관련**: 이슈 #44, [요구사항](../requirements.md) 3.3, 5.1, 5.2, [도메인 모델](../domain-model.md) `StoreDisplaySetting`, [ADR-0001](0001-store-owns-store-product-state.md)(일부 대체)

## 맥락

ADR-0001은 매장 단위의 상품 상태에 "매장별 진열 순서"를 포함했고, 요구사항·도메인 모델·API가 매니저가 매장마다 상품의 진열 순서를 정하도록 설계되어 있었다. 매니저는 완성된 최종 순서 전체를 한 번에 보내고(`StoreDisplayOrder`), Store는 같은 매장의 일괄 변경끼리 매장 단위 권고 잠금으로 직렬화하며, 목록의 모든 상품이 판매 범위에 드는지 한꺼번에 확인한다.

구현에 들어가기 전에 검토하면서, 프랜차이즈 카페는 메뉴 진열 순서가 매장마다 달라지는 경우를 찾을 수 없고 사업에 필요하지 않다고 판단했다. 반면 매장별 순서는 모델(값 객체와 불변식), 저장(컬럼과 Lazy 생성), 동시성(권고 잠금), 판매 범위의 일괄 확인, API, 매니저 화면, 테스트에 걸쳐 비용을 만든다. 카테고리의 노출 순서는 이미 본사가 정하는 값으로 Catalog에 두기로 했다.

## 결정

- **매장별 진열 순서를 두지 않는다.** 매니저가 정하는 설정은 노출·숨김과 수동 품절뿐이다.
- 메뉴와 매니저 화면의 상품은 **본사 등록 순(상품 ID 순)** 으로 놓는다. 모든 매장과 채널이 같은 순서를 본다. Catalog는 상품 ID가 등록 순으로 커지는 것을 보장한다(요구사항 7.1).
- 채널의 화면이 보조 정렬을 하는 것은 채널의 몫이고 Store는 관여하지 않는다.
- 본사가 상품 순서를 정하는 기능은 필요해지면 만드는 후속 요구사항으로 남긴다. Catalog가 상품의 진열 순서를 갖고 표시용 상품 정보에 담아 주면 Store가 메뉴를 만들 때 그 순서로 정렬하며, Store에 저장할 값은 없다. 요구사항의 "결정이 필요한 것"에 올려 둔다.

## 검토한 대안

- **매장별 진열 순서를 유지한다**: 매니저가 자기 매장의 배치를 정할 수 있다. 하지만 매장마다 다른 순서가 필요한 사업 요구가 없고, 위의 모델·저장·동시성·API 비용을 모두 치러야 한다.
- **본사가 상품 순서를 지금 정한다**: 신메뉴의 위치를 본사가 정할 수 있다. 하지만 지금 요구에 없고 Catalog에 상품 진열 순서를 새로 만들어야 한다. 필요해지면 위의 후속 요구사항으로 추가한다.

## 결과

- **얻는 것**
  - 모델이 단순해진다. 매장별 설정에 노출·숨김만 남고, 진열 순서 값 객체·불변식·일괄 변경 API·권고 잠금이 없어진다.
  - 매니저의 설정 변경이 한 상품씩이라 판매 범위 확인도 한 상품씩이면 된다.
  - 모든 매장과 채널의 메뉴가 같은 순서로 보인다.
- **감수하는 것**
  - 본사도 지금은 상품 순서를 바꿀 수 없다. 신메뉴는 항상 뒤에 놓인다.
  - 점주의 매장별 배치 같은 매장 간 차별화는 할 수 없다.
- **후속 작업**
  - 본사의 상품 진열 순서(후속 요구사항, Catalog 변경 포함)
  - 코드 정리: `AdvisoryLockNamespace`의 진열 순서 상수, 더 이상 쓰이지 않는 `CheckProductSellableUseCase.checkAll`과 `CatalogProductRepository.findByIdsForShare` 제거
