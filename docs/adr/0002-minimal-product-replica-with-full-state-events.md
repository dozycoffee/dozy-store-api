# ADR-0002: Catalog 상품은 판단에 필요한 최소 상태만 복제하고, 이벤트는 상태 전체를 담는다

- **상태**: 채택
- **날짜**: 2026-10-06
- **관련**: [ADR-0001](0001-store-owns-store-product-state.md)(매장 상품 상태의 소유), [요구사항](../requirements.md) 3.1, 3.5, 5.1, 5.2, 7.1, 8.2, [시나리오](../scenarios.md) S5, S6, [도메인 모델](../domain-model.md) `CatalogProduct`·`PendingInventoryEvent`, [ERD](../erd.md) 동시성 처리

## 맥락

매장별 진열 설정·판매 가능 여부·노출 판단을 Store가 소유하면서(ADR-0001), Store의 거의 모든 동작이 Catalog 상품의 값을 필요로 하게 됐다.

| Store의 동작 | 필요한 Catalog 값 |
|---|---|
| 노출 판단 1·2단계, 손님 메뉴 | 상품 상태, 판매 범위 |
| 매니저의 설정 변경 허용 여부 | 판매 범위 |
| 판매 범위에서 빠진 매장의 설정 정리 | **판매 범위가 바뀌었다는 사실** |
| 재고 이벤트의 상품 찾기, 반영 여부 | SKU, 재고 추적 여부 |
| 노출 현황의 매장 수 | 모든 상품의 상태와 판매 범위 |
| 매니저 화면·손님 메뉴의 표시 | 이름, 이미지, 가격, 카테고리, 태그, 유효 옵션 구성 |

이 값을 어떻게 가져올지 정해야 했다. 고려한 제약은 다음과 같다.

- 판매 범위 정리는 변경이 일어났다는 것을 알아야 일어난다. 조회만으로는 Store가 변경을 놓친다.
- 재고 이벤트는 요청과 관계없이 들어오고, 노출 현황은 모든 상품을 본다. 요청마다 Catalog를 부르면 Catalog 장애가 Store 전체로 번진다.
- 표시용 정보는 양이 많고 자주 바뀐다. 옵션 그룹 하나만 바꿔도 연결된 상품 수백 개의 유효 옵션 구성이 바뀐다.
- 메시지는 중복되거나 순서가 바뀌어 도착할 수 있다.

## 결정

- **판단용 상태만 이벤트로 복제한다.** 상품 ID, SKU, 상태, 판매 범위, 재고 추적 여부를 `CatalogProduct`로 둔다. 노출 판단, 설정 변경 허용, 판매 범위 정리, 재고 매칭, 노출 현황은 모두 이 복제본으로 한다.
- **표시용 정보는 복제하지 않고 필요할 때 조회한다.** 매니저 화면은 요청마다 Catalog 내부 조회 API를 부르고, 손님 메뉴는 짧게 캐시한다(ADR-0004). 판단용 상태는 캐시하지 않는다.
- **이벤트는 바뀐 부분이 아니라 상태 전체를 담고, 상품별 순번을 가진다.** Store는 복제본보다 순번이 큰 이벤트면 상태 전체를 교체하고, 같거나 작으면 버린다. 이벤트 종류(등록, 활성화, 단종, 판매 범위 변경)는 기록용이고 반영 방식은 같다.
- **삭제는 행을 지우지 않고 표시한다.** 늦게 도착한 오래된 이벤트로 상품이 되살아나지 않게 한다.
- **판매 범위 정리는 이전 범위와 비교하지 않는다.** 이 상품의 매장 설정 중 새 판매 범위에 들지 않는 매장의 것을 지운다. 전체 매장 목록이 필요 없고, 여러 번 해도 결과가 같다.
- **복제본을 처음 채우거나 다시 맞출 때도 같은 방식이다.** Catalog의 전체 상품 상태 목록을 이벤트와 같은 형태·순번으로 받아 같은 처리로 반영한다.
- **(2단계, 재고 연동 때) 상품보다 먼저 도착한 재고 이벤트는 보관한다.** 복제본에 없는 SKU의 이벤트는 (매장, SKU)마다 가장 늦은 것 하나만 두었다가, 그 상품이 처음 복제될 때 반영한다. 보관과 복제가 겹치지 않도록 SKU 단위 권고 잠금으로 직렬화한다.

## 검토한 대안

- **복제하지 않고 요청마다 조회**: Catalog 계약이 가장 작다. 하지만 판매 범위 정리는 변경을 알 수단이 없어 결국 이벤트가 필요하고, 재고 이벤트·노출 현황·손님 메뉴가 모두 Catalog 호출에 묶여 Catalog 장애가 Store 전체로 번진다.
- **표시용 정보까지 모두 복제**: Catalog가 죽어도 Store가 모든 화면을 보여 줄 수 있다. 하지만 상품 필드가 바뀔 때마다(예약 적용 포함) 이벤트가 필요하고, 옵션 그룹 변경 하나가 연결 상품 수백 개의 이벤트로 퍼져 계약과 처리량이 크게 늘어난다.
- **바뀐 부분만 담는 이벤트(활성화됨, 판매 범위 바뀜 각각)**: 메시지가 작다. 하지만 종류가 다른 이벤트끼리 순서가 뒤바뀌면 문제가 생긴다. "판매 범위 바뀜"(순번 5)이 "활성화됨"(순번 6)보다 늦게 오면, 순번으로 버리는 순간 판매 범위 변경을 잃는다. 순서 보장만 믿기에는 재처리·복구 상황이 위험하다.
- **이전 판매 범위와 비교해 빠진 매장을 계산**: 바뀐 매장만 처리해 효율적이다. 하지만 `ALL → LIMITED`처럼 범위가 줄어들 때 전체 매장 목록이 필요하고, 중복 이벤트나 다시 맞추기에서 결과가 달라질 수 있다.
- **모르는 SKU의 재고 이벤트는 버림**: 단순하다. 하지만 상품 등록 이벤트보다 재고 이벤트가 먼저 오면 그 재고는 다음 변동까지 반영되지 않아, 재고가 있는데 품절로 보인다.

## 결과

- **얻는 것**
  - Store의 판단이 Catalog 가용성과 분리된다. Catalog가 잠시 죽어도 진열·숨김·품절 변경, 재고 반영, 노출 판단은 계속된다.
  - 메시지 중복·순서 역전·다시 맞추기를 한 가지 처리(순번 비교 후 상태 교체)로 견딘다.
  - Catalog에 요구하는 이벤트가 상품 상태 다섯 가지 값으로 작게 유지된다.
- **감수하는 것**
  - 복제본은 결과적 일관성이다. 단종·판매 범위 변경이 반영되기까지 지연이 있다(목표치로 관리, 요구사항 3.1).
  - Catalog가 아웃박스, 상품별 순번, 등록·삭제 이벤트, 전체 상품 상태 목록 API를 새로 갖춰야 한다.
  - 매니저 화면과 손님 메뉴의 표시는 여전히 Catalog 조회에 기대므로, Catalog가 응답하지 않으면 그 조회가 실패한다(손님 메뉴는 캐시로 완화).
  - (2단계) 보관 재고 이벤트의 기한과 만료 처리를 정해야 한다.
- **후속 작업**: 메시징 기술과 서비스 공통 이벤트 규약이 정해지면 이벤트 형식을 확정한다. 복제본을 처음 채우는 절차를 운영 문서로 쓴다.
