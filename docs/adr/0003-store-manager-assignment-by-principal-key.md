# ADR-0003: 매장 매니저는 직책 없이 (매장, principal key)로 지정하고, Store는 Auth를 호출하지 않는다

- **상태**: 채택
- **날짜**: 2026-10-06
- **관련**: [요구사항](../requirements.md) 1.3, 2장, [시나리오](../scenarios.md) S3, [도메인 모델](../domain-model.md) `StoreManagerAssignment`, [ERD](../erd.md) `store_managers`, [API](../api/manager.md)

## 맥락

매장 설정(진열 순서, 노출 여부, 수동 품절)을 누가 바꿀 수 있는지 정해야 했다. 인증 쪽 전제는 다음과 같다.

- 파트너(점주)에게는 role이 없고, 매장과 점주의 관계는 Store가 관리한다. 토큰에는 매장 정보가 없다.
- 서비스는 주체를 항상 principal key(`principalType`, `principalId`)로 다룬다. 계정 ID는 종류와 관계없이 전역에서 유일하다.
- 직원 토큰의 `aud`는 가진 role의 서비스로 정해진다. Store role이 없는 직원은 Store를 부를 수 없다.

Store 쪽 사정은 다음과 같다.

- 가맹점은 점주가 운영하지만, **직영점은 점장이 운영하고 점장은 회사 직원**이다. 직원은 퇴사 처리와 감사 추적을 위해 직원 계정 하나로 다뤄야 한다.
- 지금 규칙에는 점주와 점장의 권한 차이가 없다. 둘 다 매장 설정을 관리한다.
- 서비스 사이의 의존을 줄이는 방향(요구사항 6장의 "본사 화면이 두 서비스의 결과를 합친다" 등)으로 정해 왔다.

## 결정

- **매니저 지정은 (매장, principal key) 한 쌍이다.** 직책(점주/점장)을 두지 않는다. 지정할 수 있는 계정 종류는 `partner`와 `employee`이고, 어느 쪽이든 같은 권한을 가진다. 한 계정이 여러 매장을, 한 매장이 여러 계정을 가질 수 있다.
- **인가는 역할과 매니저 지정으로 한다.**
  - `store:admin`: 모든 매장 읽기·쓰기
  - `store:viewer`: 모든 매장 읽기
  - 그 밖의 요청자: 토큰의 principal key와 **종류·ID가 모두 같은** 매니저 지정이 그 매장에 있어야 한다
  - 직원 매니저는 Store를 부를 수 있도록 `store:manager`를 받는다. 이 역할만으로는 어떤 매장도 다룰 수 없다.
- **Store는 Auth를 호출하지 않는다.** 지정 요청의 principal key를 그대로 저장하고 계정이 있는지 묻지 않는다. 계정을 찾고 본인인지 확인하는 일, 매니저 목록에 이름을 붙이는 일은 본사 화면(또는 BFF)이 Auth로 한다. Store는 UUID 형식과 계정 종류만 확인한다.
- **지정 관계는 Store 애그리거트와 나눈다**(`StoreManagerAssignment`). 지킬 규칙이 "같은 쌍 중복 금지"뿐이라 DB PK로 지키고, 매니저 변경이 매장 정보를 잠그지 않게 한다.
- 폐점한 매장에는 새로 지정할 수 없다. 이미 있던 지정은 남아 매니저가 읽기 전용으로 본다.
- 지정되지 않은 매장 요청은 `404 STORE_NOT_FOUND`로 거부해 다른 매장의 존재를 드러내지 않는다.

## 검토한 대안

- **점주와 점장을 직책으로 나눔**: 화면에 "점주 김OO, 점장 이OO"를 구분해 보여 주고, 나중에 직책별 권한을 나누기 쉽다. 하지만 지금은 권한 차이가 없어 구조만 복잡해진다. 계정 종류(파트너/직원)로 화면 구분은 할 수 있고, 직책별 권한이 생기면 지정에 직책 컬럼을 더하면 된다(인가 로직은 그대로).
- **직영 점장에게 파트너 계정을 만들어 직원 계정과 연동**: 매장 운영 앱이 파트너 로그인 하나로 끝난다. 하지만 한 사람이 계정 두 개를 갖게 되어, 퇴사 때 둘 다 막지 않으면 퇴사자가 매장을 계속 다룰 수 있다. Auth는 realm이 다르면 다른 주체로 다루므로 두 계정을 잇는 기능도 새로 만들어야 한다.
- **직영 점장에게 매장 관리 권한(`store:admin`)**: 새 개념이 필요 없지만 모든 매장을 다룰 수 있어 범위가 너무 넓다.
- **Store가 지정할 때 Auth에 계정을 확인**: 없는 계정을 지정하는 실수를 막는다. 하지만 Store가 Auth에 의존하게 되고, 지금 Auth의 파트너 조회는 system token 전용이며 직원 조회는 없다. 없는 계정이 지정돼도 그 계정으로 받을 토큰이 없어 위험하지 않다.
- **계정 ID만 비교**: ID가 전역에서 유일해 실제 충돌은 없다. 하지만 Auth 계약(principal key로 다룸)과 어긋나고, Store가 계정을 확인하지 않으므로 종류까지 맞춰 보는 것이 잘못 넣은 지정을 걸러 내는 작은 안전장치가 된다.

## 결과

- **얻는 것**
  - 점주와 직영 점장을 한 가지 규칙으로 다룬다. 같은 API, 같은 인가다.
  - 직원은 직원 계정 하나로 일하므로 퇴사하면 Auth에서 비활성화되는 즉시 막힌다.
  - Store가 Auth를 호출하지 않아 Auth 장애가 매니저 지정에 번지지 않는다.
- **감수하는 것**
  - 없는 계정이 지정될 수 있다. 본사관리자가 해제해야 한다.
  - 탈퇴·퇴사한 계정의 지정이 남는다. Auth가 비활성화를 알려 주기 전까지는 수동으로 해제한다.
  - 매장 운영 앱은 파트너 로그인과 직원 로그인을 둘 다 지원해야 한다.
  - 본사 화면이 Auth에서 계정을 찾을 수단이 필요하다(BFF 대리 호출 또는 Auth의 조회 역할).
- **후속 작업**: Auth에 Store 역할 등록, 본사 화면의 계정 찾기 방법, 계정 비활성화 알림을 요청한다. 직책별 권한이 필요해지면 새 ADR로 직책을 더한다.
