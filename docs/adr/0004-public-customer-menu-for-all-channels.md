# ADR-0004: 손님 메뉴는 채널과 관계없이 로그인 없는 공개 리소스 하나로 제공한다

- **상태**: 채택
- **날짜**: 2026-10-06
- **관련**: [요구사항](../requirements.md) 1.4, 4장, 5.2, [시나리오](../scenarios.md) S8, [API](../api/public.md), [ADR-0002](0002-minimal-product-replica-with-full-state-events.md)(표시용 정보는 조회)

## 맥락

손님이 매장과 메뉴를 보는 채널(앱, 웹, 키오스크, POS)은 정해지지 않았다. Auth의 `customer` realm도 보류 상태다. 그래도 Store가 손님 메뉴를 제공하기로 했으므로 받아 가는 방식을 정해야 했다.

- 같은 매장이라면 어느 채널로 보든 살 수 있는 상품, 품절 여부, 가격과 옵션이 같아야 한다.
- 메뉴는 매장에 가면 누구나 보는 정보다. Store는 본사 내부 정보(상품 그룹, 판매 범위)나 매니저 정보를 메뉴에 담지 않는다.
- 손님 메뉴는 트래픽이 가장 많은 경로다.
- 표시용 상품 정보와 가격 계산 규칙은 Catalog에 있다(ADR-0002). 결제 금액 계산과 검증은 주문·POS의 책임이다.
- 한 매장의 메뉴는 많아야 수백 개다.

## 결정

- **채널과 관계없이 메뉴는 하나다.** 모든 채널이 같은 API를 쓴다.
- **로그인 없이 읽는 공개 경로(`/api/v1/public/**`)로 둔다.** 매장 찾기, 손님용 매장 정보, 메뉴, 메뉴 상품 상세가 해당한다. IP 단위 요청 제한으로 남용을 막는다.
- **매장 상태에 따라 보이는 정보를 나눈다.** 개점 준비·휴업 매장은 요약만 보이고(개점 준비는 개점 예정일 포함), 상세 정보와 메뉴는 `Open`인 매장에만 있다. 폐점 매장은 보이지 않는다. 손님용 매장 정보를 상태별 타입(`CustomerStoreView`)으로 나눠, 휴업 매장의 상세 정보가 나가는 응답을 만들 수 없게 한다.
- **메뉴는 매장의 노출 상품 전체를 한 번에 주고, 서버 필터를 두지 않는다.** 카테고리 탭, 태그 모아 보기, 판매중만 보기, 이름 검색은 채널 화면이 거른다. 그래서 메뉴에 카테고리 구조(본사가 정한 노출 순서)와 상품별 태그를 담는다.
- **옵션은 메뉴 목록에 담지 않고 상품을 고르면 따로 준다.**
- **판단은 캐시하지 않고, 표시용 정보만 캐시한다.** 매장 상태, 상품 상태, 판매 범위, 숨김, 품절은 Store의 현재 값으로 판단한다. Catalog의 표시용 정보는 짧게 캐시하고, 공개 응답에는 짧은 `Cache-Control`을 붙여 HTTP 캐시·CDN을 쓸 수 있게 한다.
- **주문은 범위 밖이다.** 주문·POS가 자기 인증으로 처리하고 주문 시점의 가격을 다시 검증한다.

## 검토한 대안

- **채널별 API**: 채널마다 응답을 맞출 수 있다. 하지만 메뉴는 같아야 하므로 같은 판단을 여러 번 구현하게 되고, 채널이 정해지기 전에는 설계할 수도 없다. 채널별 메뉴가 실제로 필요해지면 메뉴에 채널 조건을 더한다.
- **채널마다 system token으로 인증**: 키오스크·POS 같은 기기에는 맞지만, 손님 앱·웹에는 맞지 않고 숨길 정보도 없다. 기기 인증은 주문 쪽에서 필요할 때 다룬다.
- **서버 필터(카테고리, 태그, 판매중만)**: 응답이 작아진다. 하지만 공개 응답의 캐시가 조건 조합마다 쪼개지고, 탭을 바꿀 때마다 요청이 생긴다. 메뉴는 전체를 받아도 가볍다.
- **메뉴 목록에 옵션까지 포함**: 키오스크가 한 번에 받기 편하다. 하지만 상품 수백 개의 옵션까지 담으면 응답이 몇 배로 커진다.
- **표시용 정보까지 Store에 복제하거나 메뉴 전용 읽기 모델을 둠**: Catalog 장애와 무관하게 빠르다. 하지만 이벤트가 크게 늘어난다(ADR-0002). 손님 트래픽이 실제로 커지면 읽기 모델을 다시 검토한다.

## 결과

- **얻는 것**
  - 채널이 정해지지 않아도 메뉴 API를 확정할 수 있다. 새 채널은 같은 API를 쓰면 된다.
  - 모든 채널의 메뉴가 같다는 것이 구조로 보장된다.
  - 공개 응답이라 HTTP 캐시·CDN으로 트래픽을 흡수할 수 있다.
- **감수하는 것**
  - 품절·숨김은 HTTP 캐시 시간만큼, 가격·이름은 표시용 정보 캐시 시간만큼 늦게 보일 수 있다. 결제 금액은 주문·POS가 검증하므로 틀리지 않는다. 단종·판매 범위 변경은 캐시와 무관하게 이벤트 반영 즉시 빠진다.
  - 캐시에 없는 표시용 정보를 Catalog에서 받지 못하면 메뉴 조회가 실패한다.
  - 공개 경로라 요청 제한과 남용 대응이 필요하다.
  - 카테고리 탭 순서를 위해 Catalog에 카테고리 노출 순서가 필요하다(요구사항 7.1).
- **후속 작업**: 캐시 시간과 요청 제한 수치를 운영하며 정한다. 손님 트래픽이 커지면 메뉴 읽기 모델을 검토한다.
