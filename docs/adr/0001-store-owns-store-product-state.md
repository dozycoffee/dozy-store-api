# ADR-0001: 매장 단위의 상품 상태를 Store가 소유한다

- **상태**: 채택
- **날짜**: 2026-10-06
- **관련**: [요구사항](../requirements.md) 개요, 1장, 3~6장, 7장, [도메인 모델](../domain-model.md) 경계

## 맥락

Store는 매장(존재, 영업 상태)과 매장–계정 관계(매장 매니저)를 소유한다. 상품의 정의(이름, 가격, 옵션, 카테고리), 상품 상태, 판매 범위(본사가 어느 매장에 팔게 할지)는 Catalog가 소유한다.

그 사이에 "매장에서 각 상품을 어떻게 보여 주고 파는가"가 있다. 매장별 진열 순서, 노출·숨김, 품절, 손님에게 보이는지(노출 판단), 손님 메뉴, 매장별 노출 현황이다. 이것을 어느 서비스가 가질지 정해야 했다.

- 노출 판단에는 매장 상태가 들어간다. 개점 준비·휴업·폐점 매장의 상품은 손님에게 노출하지 않는다(요구사항 4장 0단계).
- 매장 매니저의 요청(진열·품절 변경)은 매니저 지정으로 인가하는데, 매니저 지정은 Store의 데이터다.
- 손님 메뉴는 매장 단위로 만들어지고 매장 정보(영업 상태, 전화번호)와 함께 보인다.
- 판매 범위는 매장별 상품 상태를 정할 때 필요하지만, 본사의 상품 정책이므로 Catalog에 남아야 한다.

## 결정

- **매장 단위의 상품 상태는 Store가 소유한다.** 매장별 진열 설정, 매장별 판매 가능 여부, 노출 판단, 손님 메뉴, 매장별 노출 현황 집계가 해당한다.
- **상품의 본사 정의와 판매 범위는 Catalog에 남는다.** Store는 판단에 필요한 상품 상태(상품 ID, SKU, 상태, 판매 범위, 재고 추적 여부)를 Catalog 이벤트로 받아 둔다([ADR-0002](0002-minimal-product-replica-with-full-state-events.md)). 이름·가격·옵션 같은 표시용 정보는 Catalog에서 조회한다.
- **가격 계산 규칙(유효 옵션 구성, 표시용 시작가)은 Catalog의 것이다.** Store는 계산 결과를 받아 그대로 보여 준다. 매장별 가격은 없다.
- **판매 범위에서 빠진 매장의 설정 정리는 Store가 Catalog 이벤트를 받아 한다.**
- **Store는 판매 범위 대상 매장 확인을 Catalog에 제공한다.** 존재하지 않거나 폐점한 매장을 판매 범위에 넣지 못하게 하기 위해서다.

## 검토한 대안

- **매장별 상품 상태를 Catalog가 갖고 Store는 앞단만 맡음**: 서비스 간 이벤트와 복제가 필요 없고, 단종·판매 범위 변경이 같은 트랜잭션에서 반영된다. 하지만 매장 상태를 쓰는 노출 규칙을 판단하려면 Catalog가 매장 정보를 복제해야 한다. 복제는 방향만 바뀔 뿐 피할 수 없고, 매장에 관한 사실이 두 서비스에 나뉜다. 매니저의 모든 요청이 두 서비스를 거친다.
- **Catalog가 매장 정보를 복제해 판단**: 매장별 상품 상태를 Catalog에 둔 채 매장 상태만 받아 쓴다. 하지만 Catalog가 영업 상태, 매장 매니저 같은 매장 개념을 점점 더 알아야 하고, 손님 메뉴까지 맡게 된다.
- **Store가 화면 조립만 맡음**: 응답 모양만 Store가 정하고 상태는 Catalog에 둔다. 위 문제를 해결하지 못한다.

## 결과

- **얻는 것**
  - 매장에 관한 사실(매장 자체, 매장 매니저, 매장별 상품 상태)이 Store 한곳에 모인다. 영업 상태를 노출 판단에 넣는 규칙도 한 서비스 안에서 판단한다.
  - 매장 매니저의 진열·품절 변경이 Store 안에서 끝난다.
  - 손님 메뉴를 Store가 한곳에서 만든다.
- **감수하는 것**
  - 상품 상태와 판매 범위는 복제본이라, 단종·판매 범위 변경이 매장에 반영되기까지 지연이 생긴다(결과적 일관성). 주문 시점의 검증은 주문·POS의 책임이다.
  - Catalog가 상품 이벤트(유실 없음, 상품별 순서와 순번)와 내부 조회 API를 제공해야 한다(요구사항 7.1).
  - 복제본이 어긋날 수 있어 처음 채우기와 다시 맞추기 절차가 필요하다.
  - 본사의 노출 현황 화면은 Catalog의 상품 목록과 Store의 매장 수를 본사 화면(또는 BFF)이 합쳐야 한다. 매장 수로 정렬하거나 거를 수 없다.
- **후속 작업**: Catalog에 요구사항 7.1·7.2의 계약을 요청한다. Catalog 쪽 결정과 기존 매장 기능 정리는 Catalog가 자기 ADR로 다룬다.
